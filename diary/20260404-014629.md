# 20260404-014629

## 実施内容

前回日誌に残っていた既知バグを修正した。`provider.py` と `provider_execution.py` での `VV_*_API_KEY_FILE` 解決契約の不整合が対象。

`provider.py:_has_provider_secret` を修正した。`file_path` が設定済みでファイル不在/空のとき `value_env` にはフォールバックしないが、`auth_home_env` チェックは続行するようにした。これにより workflow で `VV_OPENAI_API_KEY_FILE` と `VV_CODEX_HOME` が同時に設定された環境で、key file が準備されていない場合でも `auth.json` で認証できるようになった。

`provider_execution.py:_try_resolve_api_key` を修正した。ファイル不在時に例外を投げる代わりに `None` を返すようにし、`_build_codex_env` が `auth.json` チェックに到達できるようにした。

`_execute_claude` の `finally` ブロックに `api_key_file_path is not None` ガードを追加した。Pyright の型エラーを回避するためで、実際に `is_temporary=True` かつ `api_key_file_path=None` になる経路は存在しない。

## レビューと対応

`file_path` が設定済みでファイル不在のとき `auth_home_env` チェックもスキップされる問題を指摘された。workflow では `VV_OPENAI_API_KEY_FILE` と `VV_CODEX_HOME` が同時に設定されているため、key file が準備されていないと `auth.json` も使えなくなる。`provider.py` と `provider_execution.py` の両方を修正した。

`_execute_claude` の `finally` ブロックで追加した冗長ガードについて、`is_temporary=True` のとき `api_key_file_path` は必ず `str` なので動作に影響しないと指摘された。Pyright の型エラー回避のためそのまま残した。

`VV_ANTHROPIC_API_KEY_FILE=/nonexistent` のとき provider 選択で「認証情報なし」エラーになるという指摘があった。動作としては壊れていないため対応しないと判断した。

## 見落とした原因

前回修正で「壊れた file env があっても value env を見に行く」不整合を直したが、auth_home_env も value_env と同列に扱ってしまい、file env が設定されている場合の auth_home_env フォールバックを考慮していなかった。選択層と実行層を別々に修正したため、実行層で auth_home_env にフォールバックする経路があることに気づくのが遅れた。

## 手こずったこと

`_try_resolve_api_key` を `None` 返しに変えると Pyright が `_execute_claude` の `finally` ブロックで型エラーを検出した。`_execute_claude` は `_resolve_api_key_file_path` を使っており `_try_resolve_api_key` とは無関係だが、`skip_api_key_check=True` のケースで `api_key_file_path = None` が代入されるパスが既存コードにあったため、Pyright がまとめて `str | None` と推論したことが原因だった。
