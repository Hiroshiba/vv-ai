## 発見したバグと修正

### 1. apiKeyHelper のフォーマット誤り

`provider_execution.py` の `_build_claude_settings` で `apiKeyHelper` をオブジェクト形式 `{"command": ["cat", path]}` で設定していたが、Claude Code の仕様はコマンド文字列 `"cat /path"` だった。

このため GitHub Actions 上では `Not logged in · Please run /login` エラーが発生し、Claude が実行できなかった。

ローカルテスト（セクション14〜18）では `--skip-api-key-check` を使っていたため `apiKeyHelper` 自体が設定されず、問題が発覚しなかった。

修正: `settings["apiKeyHelper"] = f"cat {api_key_file_path}"`

### 2. エラーメッセージに stdout を含めていなかった

Claude Code のエラーは stderr が空で stdout に JSON が出力される形式だったが、エラーメッセージに stderr しか含めていなかった。最初のエラーでは「Claude Code が終了コード 1 で失敗しました」とだけ表示され、原因特定に余分な手順が必要になった。

修正: `detail = proc.stderr.strip() or proc.stdout.strip()[:500]`

## 見逃しの考察

`apiKeyHelper` のフォーマットを公式ドキュメントで確認せずに推測で `{"command": [...]}` と書いてしまった。ローカルテストで `--skip-api-key-check` を使うことで問題が隠れ、GitHub Actions 初回で発覚した。

## artifact チェックで判明した問題

session tar を復号して確認したところ、Claude のセッションディレクトリが含まれていなかった。

tar 内には `git-diff.patch` / `git-staged.patch` / `git-status.txt` / `meta.json` のみで、Claude Code が `~/.claude/projects/` に保存するセッションデータが欠落していた。

原因は `provider_execution.py` の `_build_execution_result` で `provider_session_path=None` を返しているためで、セッションディレクトリの収集ロジックが未実装のままになっている。

session_id 自体は meta.json に保存されているため `--resume` で再開できる可能性はあるが、runner のワークスペースは実行ごとにクリーンアップされるため、実際にはセッション継続が機能していない状態。
