- `Codex CLI 実行ラッパーを実装する` タスクとして、Codex 実行層の接続と artifact 連携を一度進めた。

- `claude` の既存 placeholder 経路を壊していた。

- Codex 失敗時に resumable な session state を落としていた。
- setup 途中失敗で temp directory が残りうる構造だった。
- `file_change_count` と `plan_update_count` の集計が不足していた。
- 失敗時に部分 metrics を artifact へ残していなかった。
- `VV_OPENAI_API_KEY` を `CODEX_API_KEY` として Codex process env に入れており、security 前提に反していた。
- `_resolve_restored_home` の docstring と返り値の意味がずれていた。

## レビュー対応

- Claude placeholder を維持する形へ戻した。
- resume 引数順を修正した。
- 失敗時の session state 保持、cleanup、metrics 集計、docstring のずれは個別に修正した。
- ただし最後に、Codex を安全に認証させる方法が requirements と両立しないと判明したため、Codex 実行接続自体を外した。
- 結果として section 8 の `Codex CLI 実行ラッパーを実装する` は未達成のまま残す判断にした。

## 見逃しの考察

- 一番大きい失敗は、`Codex CLI 実行ラッパー` を section 8 単独で完了できるタスクだと見積もったことだった。
- 実際には section 11 の security 前提と不可分で、認証経路まで満たせなければ完了扱いにできなかった。
- にもかかわらず、先に実行をつないでから security を詰める順で進めたため、後から要件違反が発覚して接続を外すことになった。
- また、レビューで task の成立条件そのものが崩れた時点で、局所修正を続けず未達成へ戻す判断をもっと早くすべきだった。
- 途中で未接続コードを残したままにしたことで、後続 review からは stale な差分に対する指摘も呼び込みやすくなった。
- ユーザー指摘のとおり、後で再開する前提の論点は `// TODO:` として明示していれば、差分の意図と未解決点が reviewer に伝わりやすかった可能性がある。

## 手こずったこと
