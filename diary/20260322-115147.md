## 見逃しの考察

- 一番大きい失敗は、レビューを「新しい仕様の候補」ではなく「正しい答え」に近いものとして扱ってしまったこと。
- 本来は毎回、requirements、現行コード、今回のタスクの目的の 3 点を並べ、どれを守る話なのかを先に固定すべきだった。
- しかし実際には、レビューコメントを読んだ直後に、正しそうな筋書きへ飛びついてしまい、自分で根拠を再構成する前に文書へ反映しそうになる場面が何度もあった。
- その結果、「互換性を守るべきなのか」「requirements の product behavior を守るべきなのか」「今回の refactor では捨ててよいのか」という論点を毎回きれいに切り分けられなかった。
- 特に悪かったのは、現行コードに存在する入力契約と、requirements に明記された仕様と、単なる実装都合の fallback を、同じ「今あるもの」として雑に束ねてしまったこと。
- そのせいで、あるときは不要な互換性を守ろうとし、別のときは requirements で維持すべき既定動作まで削ろうとする、ぶれた判断になった。
- `provider_priority` の件は典型で、最初は「現行 config model が受ける入力を守るべき」と寄りすぎ、その後で「いや goal は internal default の除去だ」と反転した。
- ここで必要だったのは、受理入力の仕様を維持しつつ、どの層で既定順を確定するのかを冷静に分けることだったが、その中間の整理を飛ばしてしまった。
- local target の件でも、requirements が何を明示していて、現行コードが何を追加で受けていて、今回どこまで絞ってよいのかを最初に表にすべきだった。
- それをせずに、文書の書きぶりを都度いじったため、レビューから見ると「勝手に仕様を狭めている」ように見える状態を招いた。
- session fork についてはさらに悪く、requirements に明記があるにもかかわらず、現行コードに未実装であることに引っ張られて、文書に落とし切れなかった。
- これは「今のコードを整理する文書」ではなく「requirements を落とさずに refactor する仕様書」を作るという目的を、作業の途中で見失っていたことを示している。
- `workflow_dispatch` の対象 repo 制約も同様で、入力型分割の話に意識が寄りすぎて、正規化で弾くべき product rule を文書へ残し忘れた。
- 全体として、論点を横断的に管理せず、レビューのたびに局所修正で済ませようとしたのが失敗だった。
- 本来は、レビューで新しい論点が出たら、その場で文書を直す前に「requirements のどの行に紐づくか」「現行コードのどこに現れているか」「今回の goal では削除か維持か」を 1 つのメモへ蓄積するべきだった。
- それをせず、その場その場で文章だけ直したので、別の箇所との整合が崩れ、新しいレビュー指摘を呼び込んだ。
- また、文書を厚くすること自体が目的化し、どの節が requirements のどの項目を受け持つかという対応関係を明示しなかったのも悪かった。
- 結果として、文書は長くなったが、レビュー側に「ここが requirements のこのルールを担保している」と伝わる構造になりきらなかった。
- もう一つの反省は、「今のレビューで出なかった論点は十分に潰せた」と早めに見積もってしまったこと。
- 今回のタスクでは、繰り返しが大事だと明示されていたのに、実際には自分の内部レビューを十分に反復できていなかった。
- grep で nullable や default を拾うだけでは足りず、requirements の章ごとに文書への対応表を作るべきだった。
- さらに、文書だけでなく、`input.py`、`resolve.py`、`preflight.py`、`target.py`、`session.py` の責務分割を一枚の図として頭の中で固定してから書くべきだった。
- そこが曖昧なまま節を書いたので、repo 制約、provider 選択、session fork のような層をまたぐ仕様が抜けやすかった。

## 次に同じ失敗を避けるための具体策

- まず requirements から「維持すべき product behavior 一覧」を抜き出す。
- 次に現行コードから「今の受理入力」「今の internal fallback」「今の default」を別々に抜き出す。
- そのうえで各項目に対して、`維持する` `入力境界へ移す` `削除する` の 3 区分を先に決める。
- レビューで新しい指摘が来たら、まずその指摘を上の一覧のどこへ差し込むかを決める。文章を先に直さない。
- 「requirements に明記されているか」「現行コードだけの都合か」「今回の goal に必要か」を毎回 3 択で判定する。
- 仕様書を書くときは、抽象論より先に、維持する既定動作と制約を requirements の順で並べる。
- 文書の各節に、どの requirements を担保するための節なのかが分かるように書く。
- 局所修正を繰り返さず、レビューで 1 つでも構造的な穴が見えたら、章立てごと見直す。
- 「レビューが正しいか」を最初に判断し、「正しいならどの層の仕様か」を次に判断し、「どう書けば別解釈が消えるか」を最後に考える。
- 文書作業でも、コード探索の結果を短い表にしてから文章へ落とす。
