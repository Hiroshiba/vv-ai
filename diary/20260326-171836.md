# 日誌 2026-03-26

## タスク

`implement` コマンドの Issue 起点フローを実装した。

## 受けたレビューと考察

### PR 作成失敗を捕捉して標準エラーに出力するだけで再送出しない

`create_pull_request` の失敗を `GitHubClientError` で捕捉してログ出力のみにしていた。PR 作成失敗でも `finalize_status` が `"success"` になり、ユーザーに成功リアクションが返る問題。

`CommandError` に変換して再送出するよう修正した。

見逃した理由: push 失敗は `CommandError` に変換していたのに、PR 作成失敗だけログ出力にとどめた。「エラーを出力する処理を書いた」という実装感があり、再送出が必要だと気づかなかった。

### `get_default_branch` が失敗時に `"main"` にフォールバック

`origin/HEAD` が未設定のリポジトリでサイレントに `"main"` を返す問題。コーディング規約「余計なフォールバックはバグになるため書くな」にも違反する。

フォールバックを廃止し、`GitOpsError` を再送出するよう修正した。

見逃した理由: `origin/HEAD` が取れない場合を珍しいエッジケースと捉え、フォールバックで動くようにしておく方が便利と思ってしまった。規約を読んでいながら適用できていなかった。

### `_fetch_issue_title` が `None` を返してフォールバックタイトルを使う

`None` に別の意味（取得失敗）を持たせており、呼び出し元でフォールバックタイトルを使う設計。コーディング規約に違反する。

`_fetch_issue_title` を廃止し、`github_client.get_issue` を直接呼び出して `GitHubClientError` を `CommandError` に変換するよう修正した。

見逃した理由: Issue タイトル取得失敗でフロー全体を止めるべきかどうかを判断せず、「失敗しても PR だけ作れればよい」という気持ちでフォールバックを書いた。規約が「フォールバックはバグになる」と明示しているにもかかわらず、ここでも適用できなかった。
