# Issue / PR 周辺情報の読み込み指示を skill に追加

## レビュー内容

明示的なコードレビューはなかった。調査と相談の中で、以下の指摘と方針決定があった。

- GitHub コメント起動時に `confirm` や設計系コマンドへ Issue 内容が渡っていないように見える、という指摘を受けた。`requirements.md`、`src/vv_ai/prompt.py`、`src/vv_ai/command_handler.py`、各 skill を調査し、現状は Issue / PR のタイトル・本文・全コメントを provider prompt に自動投入していないことを確認した
- `implement` についても同様に調査した。Issue 起点では provider 実行後の PR タイトル作成時に Issue タイトルを読むだけで、実装前の prompt には Issue 本文が入らないことを確認した
- `src/vv_ai/prompt.py` に書く案も検討したが、Issue / PR などの周辺情報を読むかどうかは起動配線ではなく各 skill の作業規約として扱う方針になった
- `Issue・PR` ではなく `Issue / PR` 表記で統一する方針になり、Codex / Claude 両方の設計系 5 skill の処理フロー 1 行目だけを変更した

## 見逃しの考察

- 当初、`confirm-intent` や `basic-design` の「コードベース調査」に意識が寄り、Issue / PR のタイトル・本文・コメントのような周辺情報を明示的な入力として読む必要性を十分に扱えていなかった
- `prompt.py` で provider prompt に Issue 本文を埋め込む案を先に考えたが、将来 `onetask` も skill を見る設計になる前提では、skill 側に作業規約として書く方が再利用性が高い。起動経路の共通 prompt と skill の責務を分けて考えるべきだった
- 変更文面を一度詳しく提案しすぎた。AI が十分に文脈を読める前提では、skill には短い一文で十分だった

## 手こずったこと

- `vv-ai` CLI 経路と `onetask` 経路で prompt の入口が異なり、どこに書けばどの実行経路へ効くかの切り分けに少し時間がかかった
- `.codex/skills` と `.claude/skills` に同内容の skill が重複しているため、対象ファイルを漏らさず 10 件に限定する確認が必要だった
