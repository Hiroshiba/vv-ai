# Issue #10 対応: GitHub App トークンの read/write 分離

## 作業内容

`.github/workflows/vv-ai.yml` の `secrets.GITHUB_TOKEN` 依存をやめ、単一の GitHub App から read-only (`metadata: read`) と write (`contents/issues/pull-requests/workflows: write`) のインストールトークンを個別に発行する構成に変更した。これにより AI が生成した `.github/workflows/*` の変更を push できるようになる。

- job permissions を `contents: read` のみに最小化
- `Generate read-only token` を `permission-metadata: read` に限定
- `Generate write token` を新設して `workflows: write` を含む書き込みトークンを発行
- `Run vv-ai` の `GITHUB_TOKEN` を write-token の出力へ差し替え
- README の Secrets 表と App 権限要件を更新

## レビュー内容

レビュー指摘は NOTE 2 件のみで MUST-FIX なし。

- NOTE1: readonly-token が metadata のみだと private repo では AI の `gh issue view` が 403 になる。しかし requirements.md が public repo を主対象としているため MVP 的には問題なし → 修正不要と判断
- NOTE2: write-token に workflows:write が入ることで、AI の implement 出力に workflow 変更が混ざると人間レビュー前に push されうる構造的リスク。ただし AI サブプロセスには write-token が渡らず、Issue #10 の主題そのもの → 修正不要と判断

CHECKED では AI プロセスへの write token 非露出 (`_ALLOWED_ENV_KEYS` による env サニタイズ)、`create-github-app-token@v1` の input 名の正当性、README との整合を確認済み。

## 見逃しの考察

なし。レビューは既存の設計意図と一致する範囲の指摘だった。

## 手こずったこと

`actions/create-github-app-token@v1` で個別 permissions を指定する構文が記憶にあいまいで、context7 のサマリから答えが得られなかったため actions/create-github-app-token の action.yml を直接取得して input 名 (`permission-contents` / `permission-workflows` 等) を確認した。一次情報を取りに行く判断が素早くできた。
