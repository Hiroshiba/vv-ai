## 受けたレビュー

- その後、`headRepository` が本当に `null` になりうるのか、上流仕様まで追って確認するよう依頼を受けた。

## レビュー対応

- `requirements.md` の fork PR 前提と、GitHub CLI と GitHub GraphQL の upstream 仕様を読み直した。
- `headRepository` は nullable な field と判断し、`GitHubPullRequest.head_repository_full_name` を `str | None` へ変更した。
- `python -m compileall src` と、`headRepository: null` を含む stub payload で `get_pull_request(...)` が通ることを確認した。

## 見逃しの考察

- 最初は `headRepository` を push 先判定に使う将来像に引っ張られ、取得層の時点でも必ず存在する値のように扱ってしまった。
- しかし取得層で持つべきなのは push 可否の判定結果ではなく、上流 API が返す事実そのものだった。
- fork PR の設計を見ていたのに、削除済み fork や参照不能な fork でも PR 自体は読めるというケースを十分に想像できていなかった。
- 今後は downstream で欲しい不変条件と、upstream が返す raw data を最初に分けて考える。
