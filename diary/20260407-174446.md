# Claude Provider GitHub テスト全通過と sandbox ネットワーク修正

## 作業内容

セクション24 G-CL-10/20/30 テスト（Claude Provider で GitHub Issue/PR を操作）を通過させた。

## 問題と解決の経緯

### 問題1: seccomp 実行権限（前セッションで修正済み）

v2.1.92 リグレッション（anthropics/claude-code#43367）で `apply-seccomp` バイナリの実行ビットが落ちる問題。`chmod +x` workaround を追加して解決済み。

### 問題2: sandbox ネットワーク制限

seccomp 修正後も `gh issue view` が `Forbidden` で失敗し続けた。

セッション artifact を復号して調査した結果：
- `GH_TOKEN` は存在している（長さ 40 文字）
- `gh issue view` → `Post "https://api.github.com/graphql": Forbidden`
- `urllib.request` → `Tunnel connection failed`

context7 ドキュメントで原因が判明：

> Network access is managed through a proxy server that enforces domain restrictions. Only approved domains are accessible, and requests for new domains trigger user confirmation prompts.

`sandbox.enabled: true` を設定しつつ `network.allowedDomains` を指定していないため、承認済みドメインがゼロの状態だった。非対話モード（`-p`）ではプロンプトが出せないため、全ドメインがブロックされていた。

修正は `sandbox.network.allowedDomains: ["api.github.com"]` を追加するだけで解決した。

## 手こずったこと

### WebFetch deny の追いかけ

ユーザーから「`WebFetch(domain:github.com)` の deny ルールが影響しているのでは」という示唆があり、長時間調査した。結論としては deny ルールは `_build_claude_settings` で `settings["permissions"]` を丸ごと上書きする時点で消えるため、無関係だった。コードを正確に追えば早期に除外できた。

### 根本原因の特定

`allowedDomains` が未定義なら `needsNetworkRestriction` は `false` のはずという調査結果と、実際にネットワークがブロックされているという事実が矛盾しており、混乱した。最終的には context7 ドキュメントの「Only approved domains are accessible」という記述から、デフォルト動作としてネットワークがブロックされることが判明した。

### GitHub App の設定変更

調査中にユーザーが GitHub App の設定を変更した際、App がリポジトリからアンインストールされてしまい、一時的にワークフローが `Generate read-only token` ステップで 404 エラーになった。原因が vv-ai コードの変更とは無関係であることを素早く特定できた。
