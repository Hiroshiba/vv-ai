## 実施内容

- `src/vv_ai/github.py` に `GitHubClient.create_issue_comment(...)`、`create_issue(...)`、`create_pull_request(...)` を追加した。
- 3 つとも `gh api --method POST` で統一し、返却 JSON を既存の `GitHubComment`、`GitHubIssue`、`GitHubPullRequest` へ変換する処理を実装した。
- comment builder を単体関数へ切り出し、読み取り API と書き込み API の両方で再利用するようにした。
- 空文字 title や不正な repository 名は日本語エラーで即失敗させるようにした。
- レビュー指摘を受け、Issue と Pull Request の `body` は空文字を許容するよう修正した。
- `plan.md` の `Issue / PR / コメント作成を実装する` にチェックを入れた。

## 受けたレビュー

- 最初のレビューで、Issue と Pull Request の本文に `_require_non_empty_text` を使っており、GitHub が許容する title-only の作成を不必要に拒否しているという指摘を受けた。
- 修正後のレビューでは、既存挙動を壊す明確な不具合は見当たらず、追加 API と JSON 変換も現在のモデルと `gh api` の使い方に整合しているという結果だった。

- `create_issue(...)` と `create_pull_request(...)` では `title` だけを必須に戻し、`body` は空文字のまま送れるよう修正した。
- `UV_CACHE_DIR=/tmp/uv-cache uv run python -m compileall src` と fake runner を使い、空本文の Issue と Pull Request が通ることを確認した。

## 見逃しの考察

- 最初は AGENTS の `想定外は例外` と `不要なフォールバックを書かない` に引っ張られ、入力を厳しくする方向が安全だと短絡してしまった。
- しかしここで守るべきなのはローカル都合の厳格さではなく、GitHub API が受け付ける正当な入力境界だった。
- `comment` と同じ感覚で `issue` と `pull request` の本文も必須扱いに寄せてしまい、リソースごとの upstream 契約の差を潰してしまったのが見逃しの原因だった。
- 今後は入力を狭めるとき、まず upstream API の必須項目と optional 項目を明示的に分けてから helper を当てる。

## 手こずったこと

- `gh issue view` 系の GraphQL 風 field 名と、`gh api` で返る REST field 名が異なるため、既存 builder をそのまま使えず変換経路を分ける必要があった。
- Pull Request 作成結果では `headRepository` ではなく `head.repo.full_name` を見る必要があり、既存の読み取り経路との差分整理に少し時間がかかった。
