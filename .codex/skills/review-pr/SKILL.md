# PR レビュープロンプト

GitHub PR の変更差分をレビューし、高信号の指摘だけを出す。

## 処理フロー

0. 入力解析: 引数から PR 番号または URL を取得する。`gh pr view` と `gh pr diff` で PR 情報と差分を取得する
1. スコープ確認: 変更ファイル一覧を確認し、変更の目的を PR タイトル・本文から把握する
2. 規約読み込み: リポジトリの AGENTS.md を読む。存在しなければこのステップを飛ばす
3. 差分レビュー: 変更されたコードを以下の観点で順に確認する
   - 正当性: ロジックバグ、境界条件、エラーハンドリングの欠落
   - セキュリティ: 秘密値の露出、入力検証の不足、権限昇格
   - 設計: 公開面の変更が意図的か、既存の契約面との不整合
   - AGENTS.md 準拠: コーディング規約への違反
4. 裏取り: 各指摘について、該当コードと周辺を実際に読み、具体的な失敗シナリオを言語化する。シナリオを言語化できない指摘は落とす
5. 分類: 裏取りを通過した指摘を MUST-FIX / SHOULD-FIX / NOTE に分類する
6. 出力: 分類結果を報告する

## レビューの原則

- 変更されたコードだけをレビューする。変更に含まれないコードの改善提案はしない
- 指摘には必ずファイルパスと行番号を付ける
- 具体的な失敗シナリオを書けない指摘は出さない
- スタイル好み、命名の好み、コメント追加の提案は出さない
- AGENTS.md に明記された規約違反は SHOULD-FIX 以上で出す
- 推測的な指摘は出さない。コードから確認できる事実だけを扱う

## 分類基準

- MUST-FIX: 正当性バグ、セキュリティ問題、データ損失、公開面の意図しない破壊
- SHOULD-FIX: AGENTS.md 規約違反、エラーハンドリング不足、命名と実装のずれ
- NOTE: 将来の変更で問題になりうる設計判断。現時点では壊れない

## スコープ制限

- PR diff に含まれるファイルだけを対象とする
- diff に含まれない既存コードの問題は指摘しない
- CI 設定、認証設定、インフラ設定の変更は慎重に扱い、判断に迷う場合は NOTE で報告する

## 出力形式

各指摘を以下の形式で報告する:

```
### [MUST-FIX] ファイルパス:行番号

問題の説明（1-2文）

失敗シナリオ: 具体的にどう壊れるか

修正案: 具体的な修正の方向性
```

指摘がない場合は「レビュー完了。指摘なし」とだけ書く。
