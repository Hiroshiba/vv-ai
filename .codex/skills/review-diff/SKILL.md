# 差分レビュープロンプト

ローカルまたは PR の差分をレビューし、指摘と確認済み事項を報告する。

## 文章規範

- 必ず文章を書く直前に`japanese-tech-writing`スキルを実行する

## 処理フロー

1. レビュー前コンテキスト読み込み:
   - リポジトリに要件定義ファイル・ドメイン用語ファイル・コーディング規約ファイルがあれば先に読み、プロジェクトの目的、用語、レビュー基準を把握する。存在しなければこのステップを飛ばす
   - PR 対象の場合は元 Issue と親 Issue を読み、今回の PR の対象範囲と対象外を把握する。元 Issue は PR description の `Closes #N` などから辿る
2. 差分取得:
   - ローカル実行の場合: `git diff` と `git diff --staged` で変更を取得する。`git ls-files --others --exclude-standard` で untracked ファイルも取得し、その内容を読む。すべて空なら「差分なし」と報告して終了する
   - PR 対象の場合: 現時点の PR 全体 diff を `gh pr diff <番号>` で取得する。最新コミットだけ、前回レビュー以降だけ、前回指摘の修正だけに限定しない。空なら「差分なし」と報告して終了する
3. レビュー対象一覧の作成と一時ファイルへの書き出し:
   - `mkdir -p hiho_temp && mktemp -u hiho_temp/hiho.XXXXXXXXXX` で一時ファイルパスを取得する
   - 取得したパスへ変更ファイル一覧を書き出す
   - 取得したパスへ各ファイルの変更 hunk 一覧を書き出す
   - hunk 見出しは diff の `@@` 行を識別できる粒度で記録する
   - 一時ファイルには hunk ごとの確認状態欄を作る
   - 各 hunk で変更された関数、クラス、公開 API、設定、ワークフロー、データ構造を特定する
   - 判断に必要な周辺コードと直接依存を読む
   - 指摘対象は diff に限定するが、判断材料として周辺コードと直接依存を読む
4. 内部レビュー台帳の作成:
   - 各 hunk について、正当性、境界条件、エラーハンドリング、セキュリティ、公開契約、呼び出し元との整合、永続化、ファイル、暗号化、認証、GitHub API、CI、規約準拠、確認不足を確認する
   - 各観点を DONE / N/A / FINDING に分類する
   - 一時ファイルの hunk ごとの確認状態を DONE / N/A / FINDING のいずれかで埋める
   - 全 hunk の確認結果が DONE または N/A または FINDING になるまで最終出力しない
5. 指摘候補の裏取り:
   - 各候補について、該当コード、周辺コード、呼び出し元、失敗シナリオを確認する
   - 具体的な失敗シナリオを 1 つも書けない候補は問題度 1 以上にしない
   - 推測、好み、一般論、将来の理想論は指摘にしない
6. 二周目レビュー:
   - 一周目の指摘候補を見た後、もう一度一時ファイルの変更ファイル一覧と変更 hunk 一覧へ戻る
   - 一時ファイルに未確認の hunk がないことを確認する
   - 同じ原因の指摘を重複排除する
7. 評価: 裏取りを通過した各指摘に問題度と自信度を付ける
8. 最終確認:
   - 一時ファイルを読み返す
   - 全 hunk の確認状態が DONE または N/A または FINDING で埋まっていることを確認する
   - 未確認の hunk が残っている場合は最終出力しない
9. 出力: 評価結果を報告する。レビュー範囲サマリ、確認 hunk 数、未確認事項、問題度 0 のサマリは必須にしない

## レビューの原則

- 変更されたコードだけをレビューする。変更に含まれないコードの改善提案はしない
- 指摘には必ずファイルパスと行番号を付ける
- 確認したが具体的な失敗シナリオを書けない項目は問題度 0 とし、確認した観点と判断理由を記載する
- スタイル好み、命名の好み、コメント追加の提案は出さない
- 規約ファイルに明記された規約違反は問題度 4 以上で出す
- 推測的な指摘は出さない。コードから確認できる事実だけを扱う
- 修正案は書かない
- 元 Issue や親 Issue が対象外と示している項目は問題度を上げず、問題度 1 以下で報告する

## 問題度と自信度

各指摘に問題度と自信度を付ける。

問題度は深刻さを表す:

- 5: 正当性バグ、セキュリティ問題、データ損失、公開面の意図しない破壊。修正必須
- 4: 規約違反、エラーハンドリング不足、命名と実装のずれ。修正推奨
- 3: 修正を要検討
- 2: 修正した方が良い
- 1: 将来の変更で問題になりうる設計判断。現時点では壊れない。修正は任意
- 0: 気になって確認したが問題ないと判断したもの。確認した観点と判断理由を記載する。修正不要

自信度は確からしさを表し、1 を全く自信がない、5 を確信しているとする。

## スコープ制限

- ローカル実行: `git diff`、`git diff --staged`、untracked ファイルに含まれるファイルだけを対象とする
- PR 対象: `gh pr diff` の出力に含まれるファイルだけを対象とする
- diff に含まれない既存コードの問題は指摘しない
- CI 設定、認証設定、インフラ設定の変更は慎重に扱い、判断に迷う場合は自信度を低く報告する

## 出力形式

指摘がある場合は以下の形式で報告する:

```markdown
## レビュー

### ファイルパス:行番号

問題の説明（1-2文）

失敗シナリオ: 具体的にどう壊れるか

【問題度 N】【自信度 N】
```

報告する指摘がない場合は以下の形式で報告する:

```markdown
## レビュー

レビュー完了。指摘なし
```

## 注意点

途中レビューや小出しの指摘を出さず、全変更ファイルと全変更 hunk の確認を終えてから最終結果だけを出す。
一時ファイルの hunk 一覧は内部確認用であり、最終レビューコメントへそのまま出力しない。
一時ファイルへ hunk 一覧を書き出せない場合は、記憶だけで代替せずレビューを進めない。
