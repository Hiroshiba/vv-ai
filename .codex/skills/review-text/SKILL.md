# 人向けテキストレビュープロンプト

ローカルまたは PR の差分に含まれる人向けテキストをレビューし、指摘と確認済み事項を報告する。バグや設計などコードの正当性は差分レビュープロンプトの担当で、ここでは扱わない。

対象は README、要件定義、設計、スキル、プロンプト、コード内コメント、エラーメッセージ、Issue / PR 本文、用語集など。コードシンボル、ファイルパス、コマンド、設定値、API 名など実装詳細を指す箇所は対象外とする。

## 処理フロー

1. レビュー前コンテキスト読み込み:
   - リポジトリに要件定義ファイル・ドメイン用語ファイル・コーディング規約ファイルがあれば先に読み、文章方針、用語、規約を把握する。存在しなければこのステップを飛ばす
   - 変更が乗っている周辺テキスト全体を読み、同じ並びにある他の項目の説明粒度と文体を把握する
   - PR 対象の場合は元 Issue と親 Issue を読み、その記載を入れる・省くという決着済みの判断を把握する。元 Issue は PR description の `Closes #N` などから辿る
2. 差分取得:
   - ローカル実行の場合: `git diff` と `git diff --staged` で変更を取得する。`git ls-files --others --exclude-standard` で untracked ファイルも取得し、その内容を読む。すべて空なら「差分なし」と報告して終了する
   - PR 対象の場合: 現時点の PR 全体 diff を `gh pr diff <番号>` で取得する。最新コミットだけ、前回レビュー以降だけに限定しない。空なら「差分なし」と報告して終了する
3. コンテキストに照らした確認:
   - 追加された文について、周辺の他項目と同じ粒度か、他所と重複していないか、読者に自明でないか、今回の範囲内か、実装詳細でなく仕様の本質か、用語化が過剰でないか、ユーザー向けでアルファベット表記の英単語を避けているかを確認する
   - 削除や変更された文について、その記載が元 Issue や親 Issue で決着済みの判断でないかを確認する
4. 指摘候補の裏取り:
   - 各候補について、文章方針・周辺の他項目・元 Issue の判断のどれに照らして問題かを言えるか確認する
   - 根拠をこのどれにも紐付けられない候補は指摘にしない
   - 好み、一般論は指摘にしない
5. 評価: 裏取りを通過した各指摘に問題度と自信度を付ける
6. 出力: 評価結果を報告する

## レビューの原則

- 周辺の他項目、文章方針、元 Issue の判断のいずれかに紐付かない指摘は出さない
- 指摘には必ずファイルパスと行番号を付ける
- 迷ったら出さない
- 削除の指摘を出すのは、他所と重複・読者に自明・今回の範囲外・実装詳細・周辺より細かい、のいずれかに該当するときだけ
- 追加の指摘は最終手段とする。他のコマンドや項目が書いていないものを、この変更にだけ要求しない。実際に仕様や契約が欠けていて、かつ同じものを周辺の他項目が書いているときだけ追加を勧める
- アルファベット表記の英単語の指摘は、自然な日本語があり、かつユーザー向けの箇所だけにする
- 削除や変更の候補は、元 Issue や親 Issue で決着済みの判断でないかを必ず確認する。決着済みの記載は触らない
- 修正案は書かない。問題と根拠だけを書く
- 妥当か問われたら、前の指摘を弁護せず、文章方針・周辺の他項目・元 Issue から判断し直す

## 問題度と自信度

各指摘に問題度と自信度を付ける。テキストレビューは正当性バグを扱わないため、問題度は 4 を上限とする。

問題度は深刻さを表す:

- 4: 明文化された文章方針への違反。他所との重複、読者に自明、今回の範囲外、実装詳細、周辺と粒度が明確にずれる、ユーザー向けのアルファベット表記の英単語。修正推奨
- 3: 方針違反に近いが、修正を要検討
- 2: 文体や粒度の好みに寄る判断。現時点で方針違反とまではいえない
- 1: 好みの範囲で、修正は任意
- 0: 追加や変更を検討したが、周辺の他項目や元 Issue に照らして不要と判断したもの。確認した観点と判断理由を記載する。修正不要

自信度は確からしさを表し、1 を全く自信がない、5 を確信しているとする。

## スコープ制限

- ローカル実行: `git diff`、`git diff --staged`、untracked ファイルに含まれるファイルだけを対象とする
- PR 対象: `gh pr diff` の出力に含まれるファイルだけを対象とする
- 差分に含まれない既存テキストの改善提案はしない

## 出力形式

指摘がある場合は以下の形式で報告する:

```markdown
## テキストレビュー

### ファイルパス:行番号

問題の説明（1-2文）

根拠: 文章方針・周辺の他項目・元 Issue のどれに照らして問題か

【問題度 N】【自信度 N】
```

報告する指摘がない場合は以下の形式で報告する:

```markdown
## テキストレビュー

レビュー完了。指摘なし
```

## 注意点

途中の小出しの指摘を出さず、全テキスト変更の確認を終えてから最終結果だけを出す。
バグ、セキュリティ、設計、規約準拠などコードの正当性は扱わない。それらは差分レビュープロンプトの担当とする。
