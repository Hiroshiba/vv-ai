# 差分レビュープロンプト

ローカルまたは PR の差分をレビューし、指摘と確認済み事項を報告する。

## 処理フロー

1. レビュー前コンテキスト読み込み:
   - リポジトリに要件定義ファイル・実装計画ファイル・規約ファイルがあれば先に読み、プロジェクトの目的、実装方針、レビュー基準を把握する。存在しなければこのステップを飛ばす
   - API keys や credentials は読まない
2. 差分取得:
   - ローカル実行の場合: `git diff` と `git diff --staged` で変更を取得する。`git ls-files --others --exclude-standard` で untracked ファイルも取得し、その内容を読む。すべて空なら「差分なし」と報告して終了する
   - PR 対象の場合: 現時点の PR 全体 diff を `gh pr diff <番号>` で取得する。最新コミットだけ、前回レビュー以降だけ、前回指摘の修正だけに限定しない。空なら「差分なし」と報告して終了する
3. レビュー対象一覧の作成:
   - 変更ファイル一覧を作る
   - 各ファイルの変更 hunk 一覧を作る
   - 各 hunk で変更された関数、クラス、公開 API、設定、ワークフロー、データ構造を特定する
   - 判断に必要な周辺コードと直接依存を読む
   - 指摘対象は diff に限定するが、判断材料として周辺コードと直接依存を読む
4. 内部レビュー台帳の作成:
   - 各 hunk について、正当性、境界条件、エラーハンドリング、セキュリティ、公開契約、呼び出し元との整合、永続化、ファイル、暗号化、認証、GitHub API、CI、規約準拠、確認不足を確認する
   - 各観点を DONE / N/A / FINDING に分類する
   - 全 hunk の確認結果が DONE または N/A または FINDING になるまで最終出力しない
5. 指摘候補の裏取り:
   - 各候補について、該当コード、周辺コード、呼び出し元、失敗シナリオを確認する
   - 具体的な失敗シナリオを 1 つも書けない候補は指摘にしない
   - 推測、好み、一般論、将来の理想論は指摘にしない
6. 二周目レビュー:
   - 一周目の指摘候補を見た後、もう一度変更ファイル一覧と変更 hunk 一覧へ戻る
   - 未確認の hunk がないことを確認する
   - 同じ原因の指摘を重複排除する
7. 分類: 裏取りを通過した指摘を MUST-FIX / SHOULD-FIX / NOTE に分類する
8. 出力: 分類結果を報告する。レビュー範囲サマリ、確認 hunk 数、未確認事項、CHECKED サマリは必須にしない

## レビューの原則

- 変更されたコードだけをレビューする。変更に含まれないコードの改善提案はしない
- 指摘には必ずファイルパスと行番号を付ける
- 具体的な失敗シナリオを書けない指摘は CHECKED として報告する
- スタイル好み、命名の好み、コメント追加の提案は出さない
- 規約ファイルに明記された規約違反は SHOULD-FIX 以上で出す
- 推測的な指摘は出さない。コードから確認できる事実だけを扱う
- 修正案は書かない

## 分類基準

- MUST-FIX: 正当性バグ、セキュリティ問題、データ損失、公開面の意図しない破壊
- SHOULD-FIX: 規約違反、エラーハンドリング不足、命名と実装のずれ
- NOTE: 将来の変更で問題になりうる設計判断。現時点では壊れない
- CHECKED: 気になって確認したが問題ないと判断したもの。確認した観点と判断理由を記載する

## スコープ制限

- ローカル実行: `git diff`、`git diff --staged`、untracked ファイルに含まれるファイルだけを対象とする
- PR 対象: `gh pr diff` の出力に含まれるファイルだけを対象とする
- diff に含まれない既存コードの問題は指摘しない
- CI 設定、認証設定、インフラ設定の変更は慎重に扱い、判断に迷う場合は NOTE で報告する

## 出力形式

指摘がある場合は以下の形式で報告する:

```markdown
## レビュー

### [MUST-FIX] ファイルパス:行番号

問題の説明（1-2文）

失敗シナリオ: 具体的にどう壊れるか
```

MUST-FIX / SHOULD-FIX / NOTE / CHECKED のいずれも該当しない場合は以下の形式で報告する:

```markdown
## レビュー

レビュー完了。指摘なし
```

## 注意点

途中レビューや小出しの指摘を出さず、全変更ファイルと全変更 hunk の確認を終えてから最終結果だけを出す。
